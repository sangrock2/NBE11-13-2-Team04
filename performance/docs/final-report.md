# Iter 백엔드 부하·동시성 테스트 보고서

> 이 문서는 현재 쿼리·인덱스 및 관리자 커서 최적화 이전의 기준 측정 결과다. 최적화 효과는 같은 DB snapshot과 환경에서 다시 측정한 뒤 별도로 비교해야 한다.

## 1. 결론

- 로컬 통합 환경의 **최대 안정 처리량은 약 240 RPS**다.
- 약 **250 RPS에서 처리량이 포화**되고, 260 RPS부터 응답 대기와 Dropped iteration이 증가했다.
- 200 RPS 순간 부하는 오류 없이 처리하고 정상 수준으로 회복했다.
- 20 RPS, 30분 Soak에서 오류, 커넥션 대기, 뚜렷한 메모리 누수 징후가 없었다.
- 인증 세션 12,124건은 모두 성공했다.
- 동시성 7종 중 5종은 통과했고, 대여 승인과 동일 기간 대여 생성에서 정합성 결함을 발견했다.

이 결과는 애플리케이션, MySQL, k6를 같은 Windows PC에서 실행한 값이다. 운영 환경의 절대 수용량으로 일반화하지 않는다.

## 3. 주요 성능 결과

### 정상·지속 부하

| 시나리오 | 구성 | 평균 | p95 | p99 | 실패 | Dropped |
|---|---|---:|---:|---:|---:|---:|
| Mixed | 5→20 RPS | 23.72ms | 72.33ms | 85.01ms | 0 | 0 |
| Stress | 최대 120 RPS | 25.69ms | 77.80ms | 100.72ms | 0 | 0 |
| Spike | 20→200→20 RPS | 27.81ms | 89.59ms | 130.45ms | 0 | 0 |
| Soak | 20 RPS, 30분 | 23.19ms | 69.13ms | 82.14ms | 0 | 0 |

- 120 RPS 유지 구간 p95는 84.55ms, Hikari pending은 0이었다.

- Soak의 Heap 평균·최대는 155.78 MiB·259.43 MiB였고 GC pause 총합은 약 0.337초였다.

## 4. 최대 처리 한계

소유권이 일치하는 단일 사용자 fixture로 220→240→260→280 RPS를 측정했다.

| 목표 | 실제 처리량 | p95 관찰값 | Dropped | Hikari pending | 판정 |
|---:|---:|---:|---:|---:|---|
| 220 | 219~222 | 117~231ms | 0 | 대부분 0 | 안정 |
| 240 | 238~241 | 117~256ms | 0 | 0~6 | 안정 |
| 260 | 245~253 | 363ms→4.33초 | 발생 시작 | 최대 약 190 | 포화 시작 |
| 280 | 244~248 | 5.02→9.65초 | 초당 약 14~39건 | 최대 약 190 | 처리 불가 |

260 RPS부터 실제 처리량이 약 250 RPS에 머물렀다. 포화 구간에서 Hikari active는 10/10, pending은 약 190, 전체 시스템 CPU는 99~100%였다. 부하 제거 후 pending은 0, p95는 약 81ms로 회복했다.

240 RPS는 분당 14,400요청이다. 사용자당 평균 10초에 한 번 요청하면 약 2,400명, 30초에 한 번 요청하면 약 7,200명의 활성 사용자 트래픽에 해당한다. 이는 요청 빈도에 따른 단순 환산이다.

## 6. 발견된 결함

### 대여 승인

Rental을 일반 조회한 뒤 Equipment 락을 획득해 경쟁 트랜잭션이 이전 Rental version을 갱신하면서 낙관적 락 예외가 500으로 노출된 것으로 보인다.

- Rental을 상태 판단 시점에 락 범위에서 재조회
- 낙관적 락 충돌을 409로 변환
- 수정 후 성공 1건, 409 49건, 500 0건 재검증

### 동일 기간 대여 생성

Equipment를 일반 조회한 뒤 락을 획득해 `REPEATABLE_READ`의 이전 스냅샷으로 기간 충돌을 검사한 것이 유력하다. 성공 10건은 Hikari 풀 크기 10과 일치했다.

- 트랜잭션 최초 장비 조회부터 비관적 락 적용
- 기간 충돌을 최신 locking read로 확인
- 가능한 DB 불변식으로 이중 방어
- 수정 후 생성 1건, 409 49건, 중복 기간 0건 재검증

## 7. 개선 순서

1. 대여 승인 500과 동일 기간 중복 생성 수정
2. 대여 이력, 장비 검색, 관리자 목록을 `EXPLAIN ANALYZE`로 측정
3. 실행 계획을 근거로 인덱스를 한 개씩 적용
4. 쿼리 개선 후 Hikari 풀 크기 비교
5. k6와 애플리케이션·DB 실행 환경 분리
6. Smoke, 실패 동시성 2종, Mixed, 한계 측정, Spike, Soak 순서로 재검증

포화 상태에서 풀 크기만 늘리면 MySQL과 CPU 경합이 악화될 수 있으므로 쿼리와 인덱스를 먼저 확인한다.
